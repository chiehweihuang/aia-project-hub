售票與金流方案參考頁

有常駐工程師版｜亞太包容創新協會（ADALS）

  • 實測日期：2026-06-09
  • 標準：WCAG 2.2 AA
  • 主要基準：Google Lighthouse
  • 前提：本會有可長期維護的開發人力
目前閱讀：有常駐工程師版　·　另有 現況版（無工程師），那版只含免工程的現成系統。

有工程師之後，什麼改變了

現況版的核心限制是：沒有開發人力，所以只能用現成系統，而現成系統的結帳頁無障礙由廠商決定、本會改不了，只能挑分數較好的再回報廠商。

有一位能長期維護的工程師之後，這個天花板被掀開：本會可以自建結帳頁，把無障礙的主導權完全拿回來。金流商縮小成「只負責收款的嵌入元件或幕後 API」，無障礙不再外包出去。決策重點也從「要忍受哪家廠商的無障礙缺陷」變成「把它一次做對」。

可達成的證據：自建頁能做到 Lighthouse 無障礙 100。你正在看的這份參考頁就是自建的 HTML，實測 Lighthouse 無障礙 100、axe 0 違規。換句話說，自建路線的無障礙上限等同 Eventbrite（各方案最高分），而且全部在本會自己掌握。

仍然不變的限制

有工程師能解掉「無障礙不可控」與「整合複雜」，但有些限制跟有沒有工程師無關，依舊成立：

  • Eventbrite 一樣收不到台灣付費款（PayPal 國內禁令），它的角色仍只能是免費活動或國際曝光前台。
  • Stripe 仍需外國實體才能在台灣本地收款；差別是有工程師時，Stripe 的串接與訂閱管理變得可行，若本會願意承擔美國公司的設立與法稅，它的訂閱能力是各方案最強。
  • 信用卡輸入仍由金流商處理，但用嵌入式元件（TapPay Fields、Stripe Elements）可把它嵌進自家頁面、只剩卡號 iframe 屬廠商，周邊全由本會控制，遠優於現成系統的整頁導轉。
  • 電子發票與捐贈收據仍要串接財政部認可的服務（綠界、ezPay 等），但工程師可把它接進自建流程，自動開立。

有工程師時的可行方案：能做什麼、缺少什麼

自建無障礙結帳頁 + TapPay Fields + 綠界/藍新幕後取號a11y 可達 100

自建結帳頁，信用卡與會員定期定額走 TapPay Fields（嵌入、不跳轉），超商與 ATM 走綠界或藍新的幕後取號 API，電子發票走綠界或 ezPay。這是《無障礙購票流程設計指南》的藍圖。

能做到

  • 無障礙完全自控，可達 100（本頁即證明）
  • 售票、捐款、會員定期定額長在同一條自有台灣金流上
  • TapPay Fields 嵌入不跳轉、撥款 T+3、token 做訂閱會員
  • 超商與 ATM 用幕後取號，繳費說明頁自繪、也無障礙
  • 電子發票自動開立

缺少 / 成本

  • 需開發與長期維護（這正是本方案的前提）
  • TapPay 卡號 iframe 內部 a11y 無公開文件，須自行用 axe 與報讀器實測
  • TapPay 與定期定額費率需洽談
  • 初期開發時間較長

自建 + Stripe Elements（需外國實體）訂閱最強

用 Stripe 的嵌入式元件做結帳，搭配 Stripe Billing 管理會員訂閱。需先設美國公司。

能做到

  • 業界最強的訂閱與會員扣款管理、客戶自助入口
  • Stripe Elements 無障礙基線佳，工程師可補足周邊
  • 國際收款順暢

缺少 / 成本

  • 台灣需另設美國公司（法稅與維運負擔）
  • 費率疊加約 5.4%
  • 無台灣電子發票，需另接；撥款須中轉
  • 無台灣本地付款（超商、ATM）

客製化 WordPress + WooCommerce（工程師維護）a11y 94+

與現況版的 WooCommerce 同底，但由工程師客製主題與維護，維運風險大幅降低。

能做到

  • 開源生態、外掛多，售票、捐款、會員皆可
  • 無障礙自控（客製無障礙佈景主題，可超過 94）
  • 本地付款外掛齊全；工程師維護更新與安全

缺少 / 成本

  • 仍需組訂閱與電子發票外掛（部分付費）
  • 信用卡輸入仍跳轉金流頁，除非改用 TapPay Fields 客製
  • WordPress 站的長期維護成本（有工程師則可承擔）

現成 SaaS（netiCRM 等，仍可用）過渡/對照

有工程師不代表一定要自建。現成系統仍是快速起步或過渡的選擇。

能做到

  • 最快上線、零開發（netiCRM 一站包售票/捐款/會員）
  • 適合在自建系統完成前先運作

缺少

  • 無障礙仍受制於廠商（改不了，只能回報）
  • 有工程師時，通常會為了拿回 a11y 主導權而轉向自建

建議的技術架構（藍圖）

若採自建路線，最大化無障礙的組合是：

自建無障礙結帳頁（票種、報名表單、錯誤、即時朗讀、鍵盤流程、座位倒數 = 全自控）
├ 信用卡 / 定期定額會員 → TapPay Fields（嵌入、不跳轉、撥款 T+3）
├ 超商 / ATM（無卡者）→ 綠界或藍新幕後取號 API（繳費說明頁自繪）
└ 電子發票 / 捐贈收據 → 綠界或 ezPay（財政部認可）

完整的頁面層無障礙規格（語意結構、表單、彈窗、倒數計時 2.2.1、搶票驗證 3.3.8、狀態朗讀 4.1.3 等）見工程藍圖文件 accessible-ticketing-flow.md。那份文件正是為「有工程師」情境而寫。

兩個情境差在哪

同一件事，兩種人力前提下的差異
面向現況（無工程師）有常駐工程師
無障礙可控性低，受制於廠商頁面高，自建頁可達 100
主要路線netiCRM 或現成平台自建頁 + TapPay Fields + 幕後取號
售票/捐款/會員一體靠 netiCRM 一站自建在同一條自有金流
本地付款（超商/ATM）有（平台內建）有（幕後取號自繪頁）
起步速度快（設定即可）慢（需開發）
長期維護廠商負責本會工程師負責
無障礙倡議價值挑最好的 + 推廠商改自己做出標竿、可對外示範

限制（待補）

  • 嵌入元件的卡欄位 a11y 需自測：TapPay Fields 與 Stripe Elements 的 iframe 內部無公開無障礙文件，上線前須用 axe 與螢幕報讀器實測那幾個欄位。
  • 精確費率待洽詢：TapPay 與定期定額費率多為非公開，需洽談。
  • Stripe 路線需評估外國實體：法稅、撥款中轉、無台灣發票等成本要先算清楚。
  • 開發與維護承諾：自建是一個牽涉金流的系統，需要工程師長期在位，這是此情境的根本前提。
  • 真人測試：自動化只覆蓋約三到四成 WCAG，上線前仍應找身障使用者實走、用螢幕報讀器驗證。
